# 007 — a UI for plans

**Status:** built, 2026-10-06. Phase two.

## Why

A deploy's plan is long, and a terminal shows it one screen at a time, in one colour of detail.
Someone approving a deploy wants to see the whole of it, open the step they care about, and see
that step the way its own tool would show it. *(owner: "a UI for each plan")*

## Requirements

- **R1** — A plan can be opened as a page: every step in order, each with what it would create,
  change, remove or run, and which steps are waiting and for what. *(owner)*
- **R2** — Each step has its own section, and a plugin can supply the detail for it
  ([002/R8](002-plugins.md)): the bundle its resources, by type, with what happens to each. A
  plugin that supplies nothing gets the plan's changes, listed. *(owner)*
- **R3** — Destructive changes can't be missed: the page opens with how many there are, and each
  one carries the word, not only a colour. *(agreed)*
- **R4** — It works from a saved plan file, with no workspace and no credentials — the page shows
  exactly what `apply` of that file would run. *(agreed — it is what `lely show` already
  promises)*
- **R5** — A destroy plan opens the same way. *(agreed)*
- **R6** — After an apply, the same page can show the result: what each step did, and the
  overview of what exists ([004/R7](004-asset-bundle.md)), with links into the workspace. It is
  made from a result file that the same run wrote when asked to. That file is something the
  project keeps or throws away; lely never reads one back to decide anything, so it is a record,
  not state. *(agreed)*
- **R7** — Nothing secret is on the page, and by default no plugin's raw data either
  ([005/R34](005-plan-apply-destroy.md)). *(agreed)*
- **R8 — The page only shows.** It has no button that applies or destroys, and needs no server
  and no credentials. *(agreed)*
- **R9 — A plugin's own view is HTML, inside a frame lely owns.** The plugin supplies the
  detail; the header, the order of steps, the destructive count and the styling around it are
  lely's, so every plan reads the same way down to the step. *(agreed)*

## Decided

- **What kind of UI** (was D1): a web page, like `stevin ui` — one self-contained HTML file that
  opens in a browser, can be shared, and can hold a plugin's own view. Not a terminal app.
  *(owner, 2026-10-05)*
- **Reading only** (was D2): the page shows; it never applies or destroys anything — R8.
  *(owner, 2026-10-05: go with the proposals)*
- **How a plugin supplies its view** (was D3): as HTML, shown inside a frame lely owns — R9.
  *(owner, 2026-10-05: go with the proposals)*

## As built

Built on 2026-10-06. The builder's calls where the spec left room — none is the owner's yet:

- **`lely ui <file>`** writes one HTML file beside the plan (`plan.json` → `plan.html`, or
  `-o`), and opens it in a browser when run at a terminal (`--open` / `--no-open`). There is
  no server (R8): the browser opens the file.
- **No script.** The style sheet is inline and the page's own policy allows nothing else: no
  script, no image, no font, no frame. Steps fold with the browser's own `<details>`. Search
  and filters, which `stevin ui` has, are not there.
- **A plugin's view is made when the step is planned, and kept in the plan file** (format 4):
  `StepPlan.view`, HTML as text. So the page needs no plugin, no project and no workspace
  (R4), `lely ui` runs none of the project's code — a plan file from anywhere is safe to
  open — and the page is the same on any machine. A `command` step gives one as the `view`
  key of what its plan command prints.
- **"A frame lely owns" (R9) is not an `<iframe>`.** A plan file can be written by hand, so
  a view is not trusted: it is taken apart and written again from a short list of elements
  (tables, lists, text, folds), with every word escaped. No script, style, link, image or
  attribute comes through but a class from lely's own list, and what comes out is balanced,
  so nothing in a view can end the frame or stand in for lely's own lines. A view has a size:
  a million characters.
- **The view never replaces the changes (R2, R3).** lely's own list of a step's changes is
  always there, with the word *destructive* on each such line: it is what `apply` holds the
  step to. The plugin's view stands under it. The spec said a plugin that supplies nothing
  "gets the plan's changes, listed"; as built every step gets them, and a plugin adds to
  them.
- **The bundle's view** is every resource it declares, by type, with what the plan does to
  each — the ones it leaves alone too — and its id now. Keys, names and ids only: nothing of
  a resource's config (R7).
- **A run's record (R6)** is written by `lely apply -o result.json` and
  `lely destroy -o result.json`, and `lely ui result.json` makes the page of it. It is the
  same JSON as `-f json` prints, with a `result_format`. Nothing reads it back but the page.
  A run that ended before its first step leaves a record too. A record that can't be written
  is said, and changes nothing about how the run ended.

**Found in review, 2026-10-06** (the sixth, of this branch alone; each has a test):

- **A view could end its frame.** A browser doesn't close elements where a count of tags
  says they close: a `<li>` ends the one before it through whatever stands between, a table
  throws out what doesn't belong in it. A view with a `div` or a `details` in it, written
  again "balanced", ended the frame, the step and the list of steps in Chrome, and put its
  own words among lely's. A view now keeps no element the page around it is built from — no
  `div`, no `details`, no `summary` — so there is no end tag in it that could. Checked by
  having Chrome parse ten thousand random views (`tests/browser`, which needs Chrome: CI
  runs it, `mise run check` doesn't): nine in ten got out before, none does now.
- **`lely ui` wrote through a link** standing where the page goes, and over an unrelated
  `plan.html`. Every file lely writes is now written beside its place and moved there, so a
  link is replaced, not followed; and the default name is only written over when what is
  there is a page lely made. The file to read is never the file written, however it is
  spelled.
- **A run's record held the run's token** when a step that failed had printed it — the run's
  page was searched for it, the record was not. With `--github`, nothing a run says holds it.
- **A record's `outcome` was never held to its steps**: one edited to say `done` showed a
  failed run as applied, in green. It is read as one story now, or refused.
- **A view's size was held where a plugin hands it over and not where a file is read.**
- **"open" led to any https address** a result named. It leads into the run's own workspace,
  or it is text.

Not there: a page straight from `lely plan` (`lely plan -t dev -o plan.json && lely ui
plan.json` is two commands), and a page of `lely status`.

## Done when

- A plan with the bundle and a `command` step in it opens as one page: the bundle with its own
  detail, the command with the default. **Done** — and looked at in a browser, as a plan, a
  destroy plan and a run.
- The page for a plan file is the same on any machine, with the network off. **Done**: a test
  makes it from the file alone, in another folder, with the project broken.

**Found when those fixes were reviewed** (2026-10-06; each has a test):

- **The token was still in four places lely prints** with `--github`: its own progress lines,
  when a command that succeeds had printed it; the error of a plan that failed; a plan shown
  by `show --github`; and the plan of a step that could only be planned mid-run. Every line
  lely says is searched now, and every plan it shows is checked first — a plan that holds
  the token is shown by no command.
- **Writing a file beside its place broke what is no file**: `-o /dev/null`, a pipe, a file in
  a folder that can't be written to. Those are written as they were. A file marked read-only
  is left alone again; a file made again is for the same group, or for nobody else.
- **A record could still say `done` over a message that says what failed**, or name two steps
  that stopped it.

Reviewed twice by someone who didn't write it. The last fixes have not been reviewed in turn.
