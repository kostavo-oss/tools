# 003 — CI

**Status:** draft — after [002](002-apply.md).

## Why

A plan is reviewed where code is reviewed: on the pull request. Until lely can put its plan there,
the one plan for the whole deploy is something people have to go and fetch.

## Requirements

- **R1** — `lely plan -f md` and `lely show plan.json -f md` render the plan as Markdown, from the
  same plan the terminal and the JSON file show. *(design: Pipeline, CLI)*
- **R2** — A composite GitHub Action, in this repository, with a `command` input: `plan` or
  `apply`. *(design: CI)*
- **R3** — On a pull request, `plan` posts one comment that covers the bundle and every step, and
  updates that comment on later pushes instead of adding another. One comment per target.
  *(design: CI)*
- **R4** — On merge, `apply` runs the plan. Whether that is the plan the pull request showed, or
  a fresh one, is [D1](#to-decide).
- **R5** — No input is interpolated into a `run:` script: values reach the script through the
  environment, and a test enforces it, as in stevin. *(design: CI)*
- **R6** — The Action installs lely from its own checkout, so the Action and the tool it runs are
  always the same version. *(proposed — it is how stevin's Action does it)*
- **R7** — The docs show the `concurrency:` group that keeps two applies to one target from
  running at once. *(design: Failure model)*

## Not in this spec

- CI systems other than GitHub Actions (design: Non-goals)
- A lock of lely's own (design: Open questions)

## To decide

- **D1 — Which plan does `apply` run on merge?** The file the pull request produced, kept as an
  artifact — so what runs is exactly what was reviewed, and a stale one is refused — or a new
  plan made on `main`? The first is stricter and needs the artifact to be found again; the second
  is simpler and runs something nobody looked at.
- **D2 — Does a pull request from a fork get a plan?** It has no credentials. Skip quietly, or
  say so in the job summary?

## Done when

- R1–R7 each have a test; the Action's script is tested the way stevin's is, with the commands
  stubbed.
- A pull request in a real repository has carried a plan comment, and a merge has applied it.
